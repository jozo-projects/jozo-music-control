# Device authorization

The control gate reads `GET /room-device-authorization/config` from `VITE_API_BASE_URL`. Only a valid `{ "enabled": false }` disables it; the default and any failed or malformed lookup enable the gate. Configuration is refreshed every 30 seconds and on window focus, without a rebuild. The existing room PIN remains separate and unchanged.

The gate uses the configured `VITE_API_BASE_URL` request/status endpoints. It retains one random 32-byte base64url proof per room in localStorage, creates it before the request, and checks status every 30 seconds and on socket events; a lost response is retried with the same proof. Expired/revoked requests require the user to press the new-request button, which rotates the proof. Refresh rechecks status before mounting operational components. Network and server failures close the gate before approval, but preserve an already approved session while retrying; authentication and other non-transient errors close it. Other tabs share localStorage on a best-effort basis; simultaneous initial requests and stale tab displays can still race, so this is not cross-tab locking.

Proposed future enforcement contract (requires backend agreement, CORS and server-side validation): the approved proof is sent on same-origin API requests in `X-Jozo-Device-Proof` and in Socket.IO `auth.deviceProof` (never query parameters). Socket auth is sent only when its configured URL has the same origin as the API; deployments with separate origins must coordinate an explicit trusted-origin policy before rollout. The server currently does not enforce this credential. LocalStorage and same-origin JavaScript are not secure against XSS, browser extensions, or users with browser access; the proof is a bearer credential, not a device identity. Use HTTPS and avoid logging request bodies or headers. Do not treat this client gate as access control until the backend enforces it.
